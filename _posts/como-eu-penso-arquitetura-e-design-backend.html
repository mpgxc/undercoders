Architecture · Diagram Design

Deconstructing Clean Architecture

Dependências apontam para dentro: a camada de Domain não conhece ninguém, e tudo ao redor depende dela. A borda externa (Presentation / Infrastructure) toca o mundo real.

Domain

Regras de negócio centrais e lógica corporativa. Não depende de nenhuma outra camada.

entities value objects exceptions domain events enums repositories
Application

Casos de uso da aplicação. Orquestra o domínio para executar fluxos.

use cases app services commands queries external interfaces
Infrastructure

Tudo relacionado a preocupações externas e integrações concretas.

databases identity providers http clients cloud storage email message brokers repository impl.
Presentation

Ponto de entrada do sistema. Atua como composition root para DI.

api endpoints services (DI) gRPC graphql ASP.NET middleware exceptions

Feature Flow · Request Lifecycle

Fluxo completo de uma feature: Create Payment

Como as camadas interagem numa requisição real. O request entra pela borda (Presentation), desce até o Domain via casos de uso, e toda I/O externa é acessada por ports (abstract classes no Domain/Application, que servem de token de DI) implementados por adapters na Infrastructure — a Dependency Rule nunca é violada.

fluxo de chamada (entrada) retorno / dados port → adapter (DI)
Entrada · passos 1–4

1. Client faz POST /payments. 2. O Controller valida o DTO e chama o caso de uso. 3. O UseCase instancia a entidade Payment, que aplica as regras de negócio e invariantes. 4. Para persistir, o UseCase depende do port PaymentRepository — uma abstract class que atua como token de DI, não a implementação.

Saída · passos 5–7 + retorno

5. Via DI, o port é resolvido para o adapter TypeOrmPaymentRepository na Infrastructure. 6. O adapter fala com Postgres/Celcoin. 7. O resultado sobe pelo port de volta ao UseCase, que retorna ao Controller e responde 201 Created. A seta pontilhada nunca inverte a Dependency Rule: o Domain só conhece a abstract class.

Implementation · NestJS + TypeScript

O mesmo fluxo, em código

Cada bloco corresponde a uma camada do fluxo acima. Layout feature-first, convenção Result<T, E> com BusinessError semântico, e o port definido na Application implementado por um adapter na Infrastructure — a dependência aponta sempre para dentro.

}

Tactical Design · Domain-Driven Design

Visão DDD: Aggregates, Events & Bounded Contexts

A mesma feature vista pela lente do DDD tático. O Aggregate Root é a fronteira de consistência: protege invariantes, referencia outros agregados só por id, e comunica mudanças por domain events. Cada bounded context tem seu próprio modelo — o que é Payment aqui não é o mesmo Payment em Ledger.

1Aggregate Rootpayment.aggregate.ts
export class Payment extends AggregateRoot {
  private _status: PaymentStatus = 'PROCESSING';

  private constructor(
    readonly id: PaymentId,
    private readonly amount: Money,      // value object
    private readonly pixKey: PixKey,     // value object
  ) { super(); }

  // fábrica protege as invariantes do agregado
  static create(input: CreatePaymentInput): Result<Payment, BusinessError> {
    const amount = Money.of(input.amount);
    if (amount.isErr) return amount;

    const payment = new Payment(PaymentId.next(), amount.value, input.pixKey);

    // registra o evento de domínio — publicado após o commit
    payment.apply(new PaymentCreated(payment.id, amount.value));
    return ok(payment);
  }
}
2Value Objectmoney.vo.ts
// imutável, sem identidade, validado na construção
export class Money {
  private constructor(readonly cents: number) {}

  static of(value: number): Result<Money, BusinessError> {
    if (!Number.isInteger(value) || value <= 0) {
      return err({ type: 'INVALID_AMOUNT', message: 'amount inválido' });
    }
    return ok(new Money(value));
  }

  equals(other: Money): boolean { return this.cents === other.cents; }
  toCents(): number { return this.cents; }
}

Ports & Adapters · Hexagonal Architecture

Visão Hexagonal: Driving & Driven

O núcleo (domínio + aplicação) fica isolado no centro. Tudo que aciona a aplicação entra pela esquerda por driving ports (primary/input); tudo que a aplicação aciona sai pela direita por driven ports (secondary/output). Os adapters ficam do lado de fora — trocar REST por gRPC, ou Postgres por outro banco, não toca o núcleo.

Project Layout · Feature-First (Pragmatic)

Organização pragmática: vertical slice por feature

Sem quebrar tudo em camadas físicas antes da hora. Cada feature é uma fatia vertical auto-contida: um controller por feature roteia para vários use-cases numa pasta use-cases/ flat, onde cada arquivo *.use-case.ts reúne as três coisas: os tipos Input/Output e a classe. A regra de ouro do meio-termo: port só onde há I/O externa (banco, gateway, fila) — colaborador interno é classe concreta, nada de abstract class por simetria. Implementações concretas compartilhadas (datasource, cliente HTTP, SDK da Celcoin) vivem numa infrastructure/ global; os adapters específicos da feature ficam nela mesma.

Quando escalar? Extraia um port novo só quando aparecer segunda implementação, necessidade real de teste com fake, ou o colaborador passar a fazer I/O. Antes disso, classe concreta é mais simples de ler, navegar e refatorar — YAGNI aplicado à arquitetura.

CQS · Command-Query Separation

Separação CQS: Commands & Queries

A pasta de casos de uso é dividida por intenção. Command (escrita, muda estado) → um use-case dedicado por ação, que passa pelo domínio e persiste via repository. Query (leitura, sem efeito) → um query service por contexto: uma classe com vários métodos, cada um uma consulta. Como o repository é um padrão de persistência de domínio, ele pertence ao lado de command; a query pode injetar direto um database service e ler o que precisa — sem repository com métodos sob medida.

2Command · use-case por açãouse-cases/refund-payment.use-case.ts
export type RefundPaymentInput  = { paymentId: string };
export type RefundPaymentOutput = Result<Payment, BusinessError>;

@Injectable()
export class RefundPaymentUseCase {
  // escrita → passa pelo domínio e persiste via REPOSITORY
  constructor(private readonly repository: PaymentRepository) {}

  async execute(input: RefundPaymentInput): Promise<RefundPaymentOutput> {
    const payment = await this.repository.findById(input.paymentId);
    if (!payment) {
      return err({ type: 'PAYMENT_NOT_FOUND', message: 'pagamento inexistente' });
    }

    const refunded = payment.refund();      // regra de transição no domínio
    if (refunded.isErr) return refunded;

    await this.repository.save(refunded.value);
    return ok(refunded.value);
  }
}
3Query · service por contextoqueries/payments.query-service.ts
@Injectable()
export class PaymentsQueryService {
  // leitura → injeta o DATABASE direto, sem repository de domínio
  constructor(private readonly db: DatabaseService) {}

  // cada método é uma query; devolve DTO de leitura, não a entity
  listByAccount(accountId: string): Promise<PaymentListItem[]> {
    return this.db.query<PaymentListItem>(
      `SELECT id, amount_cents, status, created_at
       FROM payments WHERE account_id = $1 ORDER BY created_at DESC`,
      [accountId],
    );
  }

  async dailyTotals(accountId: string): Promise<DailyTotal[]> {
    return this.db.query<DailyTotal>(
      `SELECT date_trunc('day', created_at) AS day, SUM(amount_cents) AS total
       FROM payments WHERE account_id = $1 GROUP BY day`,
      [accountId],
    );
  }

  findDetail(id: string): Promise<PaymentDetail | null> {
    return this.db.queryOne<PaymentDetail>(
      `SELECT * FROM payments WHERE id = $1`, [id],
    );
  }
}

Por que a assimetria? O repository existe para reconstruir e persistir agregados com suas invariantes — isso só importa na escrita. Na leitura não há regra a proteger: forçar tudo por repository gera métodos findXById sob medida e mapeamento entity→DTO desnecessário. O query service lê o read model direto do banco e devolve exatamente a forma que a tela precisa. É CQS sem a complexidade de CQRS com bancos separados.

Anatomy · Use-Case, Domain Services & Result

Anatomia interna: Use-Case, Domain Services & Result Pattern

Como um use-case se organiza por dentro. Ele é um orquestrador fino: valida a entrada, delega a regra ao domínio (entity ou domain service quando a lógica cruza agregados), fala com o mundo via ports, e devolve um Result<T, E>. Esse Result é o ponto de bifurcação: ele é uma união que sempre resolve em um dos dois construtores — ok(value) (caminho feliz) ou err(error) (erro de negócio, sem exception). Qualquer etapa que falha já produz um Result na variante err, e o fluxo faz short-circuit no primeiro deles.

1Result Patternshared/result.ts
// discriminated union: sem exceptions no fluxo de negócio
export type Result<T, E> =
  | { kind: 'ok';  isOk: true;  isErr: false; value: T }
  | { kind: 'err'; isOk: false; isErr: true;  error: E };

export const ok  = <T>(value: T): Result<T, never> =>
  ({ kind: 'ok', isOk: true, isErr: false, value });

export const err = <E>(error: E): Result<never, E> =>
  ({ kind: 'err', isOk: false, isErr: true, error });

// erro de negócio semântico — mapeado p/ HTTP na borda
export type BusinessError = {
  type: 'INVALID_AMOUNT' | 'PAYMENT_NOT_FOUND' | 'INSUFFICIENT_LIMIT';
  message: string;
};
2Domain Servicedomain/payment-limit.service.ts
// stateless · regra que NÃO pertence a um único agregado
// (envolve o Payment + o limite diário da conta)
@Injectable()
export class PaymentLimitService {
  assertWithinDailyLimit(
    payment: Payment,
    todayTotal: Money,
    dailyLimit: Money,
  ): Result<void, BusinessError> {
    const projected = todayTotal.add(payment.amount);

    if (projected.isGreaterThan(dailyLimit)) {
      return err({
        type: 'INSUFFICIENT_LIMIT',
        message: 'excede o limite diário da conta',
      });
    }
    return ok(undefined);
  }
}
3Use-Case · compõe tudouse-cases/create-payment.use-case.ts
export type CreatePaymentInput  = { accountId: string; amount: number; pixKey: string };
export type CreatePaymentOutput = Result<Payment, BusinessError>;

@Injectable()
export class CreatePaymentUseCase {
  constructor(
    private readonly repository: PaymentRepository,   // port
    private readonly pixGateway: PixGateway,       // port
    private readonly limitService: PaymentLimitService, // domain service
  ) {}

  async execute(input: CreatePaymentInput): Promise<CreatePaymentOutput> {
    // 1) invariantes do agregado
    const payment = Payment.create(input);
    if (payment.isErr) return payment;              // short-circuit

    // 2) regra multi-agregado via domain service
    const today = await this.repository.totalToday(input.accountId);
    const check = this.limitService.assertWithinDailyLimit(
      payment.value, today, Money.of(500000).value,
    );
    if (check.isErr) return check;                  // short-circuit

    // 3) efeitos via ports, então devolve ok
    await this.pixGateway.dispatch(payment.value);
    await this.repository.save(payment.value);
    return ok(payment.value);
  }
}

Entity vs Domain Service: se a regra usa só o estado de um agregado, ela mora na própria entity (Payment.create). Quando precisa de dois ou mais agregados ou de dados que a entity não possui (limite diário, saldo de outra conta), vira um domain service stateless. O use-case nunca contém regra de negócio — ele só sequencia e propaga o Result.

Messaging · Outbox · Pub/Sub · Idempotency

Mensageria confiável: Outbox, Pub/Sub & Idempotência

O problema central em sistemas distribuídos: como publicar um evento e gravar no banco de forma atômica? O Transactional Outbox resolve gravando o evento na mesma transação do estado; um relay lê a tabela e publica no broker (SNS → SQS, fan-out pub/sub). Como o relay garante at-least-once, o consumidor precisa ser idempotente — processar a mesma mensagem duas vezes tem o mesmo efeito que processar uma.

1Outbox · escrita atômicaadapters/typeorm-payment.repository.ts
@Injectable()
export class TypeOrmPaymentRepository implements PaymentRepository {
  constructor(private readonly dataSource: DataSource) {}

  async save(payment: Payment): Promise<void> {
    // estado + evento na MESMA transação → atomicidade
    await this.dataSource.transaction(async (tx) => {
      await tx.save(PaymentModel, toModel(payment));

      for (const event of payment.pullEvents()) {
        await tx.insert(OutboxModel, {
          id: randomUUID(),
          type: event.type,                 // 'payment.created'
          aggregateId: payment.id,
          payload: event.payload,
          status: 'PENDING',
        });
      }
    });
  }
}
2Relay · poller → brokerinfrastructure/outbox/outbox-relay.ts
@Injectable()
export class OutboxRelay {
  constructor(
    private readonly dataSource: DataSource,
    private readonly sns: SnsPublisher,
  ) {}

  @Interval(2000) // poll a cada 2s (ou LISTEN/NOTIFY)
  async flush(): Promise<void> {
    await this.dataSource.transaction(async (tx) => {
      // concorrência segura entre réplicas do relay
      const batch = await tx.query(
        `SELECT * FROM outbox WHERE status = 'PENDING'
         ORDER BY created_at FOR UPDATE SKIP LOCKED LIMIT 100`,
      );

      for (const row of batch) {
        // messageId = id do outbox → chave de dedupe no consumidor
        await this.sns.publish(row.type, row.payload, { messageId: row.id });
        await tx.update(OutboxModel, row.id, { status: 'PUBLISHED' });
      }
    });
  }
}
3Consumer idempotenteuse-cases/on-payment-created.consumer.ts
@Injectable()
export class OnPaymentCreatedConsumer {
  constructor(
    private readonly idempotency: IdempotencyStore,
    private readonly ledger: PostEntryUseCase,
  ) {}

  @SqsMessageHandler('ledger-queue')
  async handle(message: SqsMessage): Promise<void> {
    const { messageId, payload } = parse(message);

    // 1ª camada: dedupe atômico. SETNX → false se já visto
    const firstTime = await this.idempotency.claim(messageId, { ttl: '24h' });
    if (!firstTime) return;              // duplicata → no-op, ACK

    // 2ª camada: a própria operação é idempotente por natureza
    // (UPSERT por aggregateId, não INSERT cego)
    await this.ledger.execute({ paymentId: payload.aggregateId, amount: payload.amountCents });
  }
}

Idempotência em duas camadas: a primeira é o dedupe por messageId (chave única com TTL — Redis SETNX ou tabela processed_messages), que barra o reprocessamento na borda. A segunda é tornar a própria operação idempotente (UPSERT por chave de negócio, transição de estado condicional), como rede de segurança caso o dedupe expire ou falhe. Nunca confie só numa camada.

Distributed Transactions · Saga Pattern

Saga: Orquestrada & Coreografada

Sem 2PC entre microserviços: uma saga divide a transação distribuída em passos locais, cada um com uma compensação que desfaz o efeito se um passo posterior falhar (consistência eventual). Duas formas de coordenar: orquestrada (um coordenador central manda os comandos e dispara as compensações) ou coreografada (cada serviço reage a eventos, sem coordenador — o fluxo emerge dos eventos).

1Saga Orquestrada · com compensaçõesuse-cases/payment.saga.ts
type Step = { run: () => Promise<void>; compensate: () => Promise<void> };

@Injectable()
export class PaymentSaga {
  constructor(
    private readonly funds: FundsPort,
    private readonly account: AccountPort,
    private readonly pix: PixGateway,
  ) {}

  async execute(p: Payment): Promise<Result<void, BusinessError>> {
    const steps: Step[] = [
      { run: () => this.funds.reserve(p),   compensate: () => this.funds.release(p) },
      { run: () => this.account.debit(p),   compensate: () => this.account.refund(p) },
      { run: () => this.pix.dispatch(p),     compensate: () => Promise.resolve() },
    ];

    const done: Step[] = [];
    try {
      for (const step of steps) {
        await step.run();          // cada passo é idempotente
        done.push(step);
      }
      return ok(undefined);
    } catch (e) {
      // desfaz na ordem reversa apenas o que já rodou
      for (const step of done.reverse()) await step.compensate();
      return err({ type: 'SAGA_ABORTED', message: String(e) });
    }
  }
}

Coreografada — sem coordenador: cada serviço publica um evento ao concluir seu passo, e o próximo serviço reage. Não há um lugar único que "conhece" a saga inteira; o fluxo emerge da cadeia de eventos. Simples para poucos passos, mas fica difícil de rastrear conforme cresce.

Quando usar cada uma? Orquestrada quando o fluxo é complexo, precisa de visibilidade central, timeouts e retries coordenados — o coordenador vira uma state machine testável (seu caso no Buni para fluxos de pagamento com vários passos). Coreografada quando são poucos passos e baixo acoplamento importa mais que rastreabilidade. Em ambas: passos idempotentes e compensações semânticas (um estorno, não um "delete") são obrigatórios.
